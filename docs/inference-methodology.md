# Sample evidence methodology

Atlas 3.0 is a fictional reference source bundle. Its current report uses the same structural parsers, citation checks and dashboard as actual assessments. Complete scope includes repository source, an API contract, architecture declarations and commercial terms; Essentials uses three core sources. Reference exploration never contacts a real target or creates stored rows. See `docs/workspace-observation.md` for its source contract.

Raw source records are stored independently from claims. Component references and documented relationships are explicit sample annotations. A deterministic rule builder creates the report without TinyFish, an LLM, or any outbound collection. Nothing in this model is an observation about the entered domain.

| Classification | Sample rubric score | Basis |
| --- | --- | --- |
| Observed, shown as Documented | 93 for components; 88 for explicit connections | A fictional technical reference explicitly describes the item |
| Inferred | 72 for components/entities; 68 for relationships | Supported deduction with implementation details unestablished |
| Hypothesis, shown as Proposed | 42 | Plausible connection without an explicit documented path |
| Conflicted delivery assessment | 58, inferred | Technical queue contract conflicts with broad product copy |
| Unknown | No claim/score | Insufficient source material |

Scores are transparent rubric values, not statistical probabilities. Sample annotations do not perform a general signal extraction or resolve arbitrary real-world conflicts.

The queue source describes at-least-once delivery and consumer deduplication. A second product source says exactly-once. Both source roles are retained in the disputed delivery claim, inspector, JSON, Markdown, and normalized SQLite export. Technical documentation is preferred for this specific assessment; the conflicting source remains visible.

Entities and references describe a probable logical model. Every field type remains unknown, and no database engine or physical schema is asserted. Unknowns include backend implementation, hosting/orchestration, session persistence, and undisclosed broker/search products.

SQLite exports now use schema_version 3, normalized PK/FK constraints, and supporting/contradicting evidence roles. Exports run integrity and foreign-key checks before returning bytes. Old stored reports and their original fixture provenance are preserved.

## Saved-source assessments

Imported-source reports have their own source provenance and run metadata. Explicit parsing handles OpenAPI and named header/technology declarations; optional model extraction contributes semantic candidates. Quotes must match stored passages exactly, offsets must reference owned evidence, and graph/entity relationships must resolve before promotion. Sources are user-attributed snapshots, not independently fetched observations.

The saved-source rubric uses 85 for source-explicit findings, 60 for inference, and 35 for hypotheses. Any retained contradictory source caps strength at 45. Model-generated observed classifications are downgraded when their names are not present in supporting excerpts. These values explain source strength without statistical calibration. Exact quote matching does not verify semantic entailment.

Feature mappings retain tiers, availability, limits, and opposing included/excluded statements. Private physical tables/types/constraints remain unknown. Cited questions preserve insufficient evidence, reject unmatched quotes, and record retrieval/model provenance. Evaluation compares real provider execution with the explicit-parsing baseline rather than estimating accuracy from the rubric.

Real web assessments use retrieved public documents with an independent collection record. Imports remain user-attributed. Extraction rejects headings and conservative negated assertions, resolves relations after components are known, and records bounded coverage. These are structural guards, not a complete semantic-entailment verifier.
